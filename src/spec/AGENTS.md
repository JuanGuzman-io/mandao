# src/spec — spec execution domain

Purpose: parse and evaluate spec state, task dependencies, evidence, traceability, costs and closure.
The CLI and scripts gather inputs; writer helpers own persistence.

- Copy `loop.ts` for decision logic. Return structured actions; keep side effects in scripts/CLI.
- `loop.ts` offers `choose-test-evidence` after a recorded `TESTS_PASS`; only a killed first-pass mutation
  or independent `TEST_REVIEWED` event releases implementation. Three unchanged task/action recommendations
  are halted by the CLI using the `loop_brake` progress observation; an execution or approval row resets it.
- Approval history is append-only. `activeApprovals` excludes rows targeted by a revocation/annulment event;
  `shown` rows remain snapshots, not approvals. Keep `specBudget` and `nextStep` on the effective view.
- RED evidence gates TDD; characterization uses mutation evidence. No new implementation step until
  the required evidence exists (`loop.ts`, `test/integration/tdd.test.ts`).
- Two FAILs escalate a tier; three at strong halt. Do not lower reviewer effort or silently discard
  a security blocker. Whole reviews and attempt counts come from the script-owned log (ADR 0039).
- Approval records and integrity hashes are provenance, not cryptographic identity guarantees.
- Costs distinguish actual usage and estimates; a subscription list-price equivalent is not a bill.
- Unit-test decisions and integration-test recording through temporary workspaces made by `makeTree`.
- `plan.ts`: `planTasks.parallel` lists only eligible `parallel_safe` tasks of `next`'s wave whose declared `files` overlap neither `next` nor another chosen task. Paths are normalized (`\`, `..`, `./`, leading `/`) and cut back to the folder before a glob; an empty `files` list, a path above the root or an extglob overlaps everything. It only reports: nothing runs tasks in parallel (phase 9b is pending evidence).
- `deliveries.ts` (inside a spec, MDO-0013; not `delivery.ts`, the git delivery of MDO-0012): tasks may declare `delivery: n`; none declared means one delivery and unchanged behavior. The AC a delivery meets is derived, never declared: an AC (its clauses included) belongs to the delivery of its last task, so a delivery whose tasks complete no AC is reported as a layer. `deliveryIssues`: mixed declared/undeclared tasks, numbering gaps (1..n), a dependency on a later delivery, a delivery meeting no AC. `deliveryProgress` exists only with 2+ valid deliveries and work pending; its `checkpoint` (previous delivery done, none of the current one's tasks done) is a derived boundary, never stored. `proposeDeliveries` is a forecast from declared files and task count (`deliveries.propose_above_tasks`); `pr-plan` cuts by delivery from real sizes, before waves. `planTasks.next` comes from the first unfinished delivery, even while the split is invalid (conservative; `deliveryIssues` also blocks `approve tasks`); `nextStep` names the partial verify (`verify-plan --delivery n`, which always carries a partial-plan blocker) and a new session at a boundary.
- `verify.ts`: `verifyPlan({ delivery })` is the partial verify of one delivery (MDO-0013). Suites, e2e flows, `missingRed`, not-done and security blockers cover that delivery's tasks; trace findings and deferred runs drop only what belongs to later deliveries (earlier deliveries stay). A scoped plan always carries a first `partial plan` blocker, so it never verifies the spec; `scope: { delivery, ac, tasks, clear }` says the delivery passed when `clear` is true. Errors use domain wording; the CLI owns the `--delivery` flag.
- `next.ts`: `nextStep` is pure and only recommends; it never offers implement before approval or past an open item (`NEEDS CLARIFICATION`, `CONFLICT` inline or as a Consistency Check row, a critical Consistency Check row, a pending decision; resolved rows are ignored). Lite is `spec.md` existing (`SpecFolder.lite`). Hashes ignore `status:` and `tasks.md`; a missing hash means no claim. Change-after-approval compares approval rows only; `shown` rows (`run next --shown`) are compared only by `approve --by-running`.
- `next.ts` reads only real markers: `withoutCode` (`markdown.ts`) drops inline code spans and fenced blocks first, so a marker shown as an example is not an open item. A Consistency Check row is resolved when its Status starts with `resolved` (`core/templates/shared/rules/consistency-check.md`; a test pins both). A `verify-report.md` with `verdict: blocked` recommends implement, not verify. A closed spec skips the open-item check and recommends its delivery from git (`unpushed` → push, `pushed` → PR and merge, `merged` → `none`, no options); it never offers story or clarify. `nextFor` (`src/cli/approve.ts`) reads those facts from the spec's own branch (not HEAD); only `origin/<base>` counts as merged, and without git or the branch there is no delivery fact; naming the delivery performs nothing (MDO-0012).
- `layout.ts`: `layoutManifest(version, depth)` is the one manifest behind `run layout`, the close gate (`run status <ID> closed`) and `docs/spec-anatomy.md`; the version is the story's `schema_version` (`LAYOUT_VERSIONS`, 1 or 2, anything else throws), never a `layout:` key or the files present. `tasksHaveOwnFile(schema_version)` is the one rule for where tasks live (version 2: always `tasks.md`; `docPath` in `src/scripts/spec-log.ts` calls it and never falls back to `spec.md` for them; version 1 keeps the old fallback, and any value outside `LAYOUT_VERSIONS` counts as version 1 there). New stories start at `CURRENT_LAYOUT_VERSION` (2), the last `LAYOUT_VERSIONS` entry, which `mandao start` uses and a test pins against the story template's `schema_version`. Alternatives (version 1 lite: `spec.md` or `requirements.md` + `design.md`) are `oneOf` entries in the manifest, not special cases. `layoutFindings` is pure over `{ story, docs, entries }`; `readLayout` in `src/scripts/spec.ts` reads the folder (D1). An AC with `status: removed` is skipped by `trace` and `acStatus` (ADR 0041).
- `principles.ts` is the pure design gate used by layout, trace and verify: constitution rows use stable `DP-*` IDs; v2 design/lite spec requires `writes_data`, a complete principle-check row per declared ID, and (when writes are explicit or inferred from `data-model.md` / `data` / `migration`) an ACID row plus a task-declared partial-failure test. V1 remains compatible.
- `state.ts`: `_log/state.yml` of a version 2 spec, one zod schema (`stateSchema`) with the sections `start`, `baseline`, `progress`, `approvals` and `cut_estimates` (D3, C-1, C-3). `parseState` reads an absent or empty file as empty and throws on a row that breaks its schema (never drops it; readers such as Kaizen's cut estimates and `specSpend` let that error through); `renderState` writes the sections in that order and leaves out absent ones. The IO is in `src/scripts/spec-log.ts`: `specKeepsState(dir)` (from the story's `schema_version` through the layout manifest; before the story exists, a folder with `_log/state.yml`, which `mandao start` writes, is the current layout, via `effectiveLayoutVersion` in `src/schemas/spec.ts`, and a folder with neither keeps its own files), `logPath` mapping `progress.yml`, `approvals.yml` and `session-cuts.md` to `state.yml` for version 2, and the section helpers `readState`, `updateState`, `readApprovalLog`, `appendApprovalLog`, `readProgress`. Every writer (start, baseline, checkpoint, red, commit queue, approve, `run next --shown`, cut estimates) goes through them; a version 1 spec, or a folder without a story (quick), keeps writing its own files exactly as before. `mandao start` writes `start` and `baseline` to `state.yml` for a new spec (`CURRENT_LAYOUT_VERSION`); a quick change keeps `start-<slug>.yml` and `baseline-<slug>.md`. `progressSchema.schema_version` is the progress record's own format version, always 1, separate from the spec layout version.
- `timeline.ts`: `timeline(execution, approvals)` merges the approvals into the execution rows by date (stable: execution rows first on the same instant; `shown` rows are left out). `run status <ID>` without a target and `run implement-summary` print it as `timeline`; nothing is written, and an approval never becomes an `execution.md` row (C-1).
- `costs.ts`: in a version 2 spec a new `costs.yml` entry keeps `cumulative` per role only (C-2); the per-model baseline is derived from the session's earlier `models` (`sessionModelTotals`). A version 1 spec, and the quick folder, keep the `model:` lines in `cumulative`. On both versions the per-model part of a new entry is measured against the `model:` lines of the session's last `cumulative` when it has them (version 1: the same numbers as before), else against `sessionModelTotals`, so a version 2 record followed by a version 1 or quick record in the same session is not counted twice.
- Six-file log (version 2, D3): `_log/` holds only `state.yml`, `execution.md`, `reviews.md`, `gates.md`, `premises.md` and `costs.yml`. `specLogInCache(dir)` (in `src/scripts/spec-log.ts`) picks the layout with `keepsLogCache` from `src/schemas/spec.ts`, the predicate the writer's integrity routing uses too (a quoted or unknown `schema_version` is version 1 for both); `LAYOUT_VERSIONS` and `STORY_ID` are written once there; `writeLogSection`/`logSections` read and write the merged files as `## Tn — attempt k` (reviews, `(via <harness>)` for a process review; gates) and `## Pn — run` (premises) sections, and the first state or section write creates the empty `reviews.md`, `gates.md`, `premises.md` and `costs.yml` so the six are always there. `gates.md` keeps the status table and, for FAIL/TIMEOUT gates only, at most 40 lines naming the task's files (the tail when none does; a repeat of an earlier attempt's same lines is a pointer to it); `premises.md` keeps claim, command, sha, exit and 20 lines. Everything else goes to `.mandao/cache/<ID>/` (`cachePath`, git-ignored by the managed `.gitignore` block): packs, full gate output, probes and their scratch, mutations, discrepancies and `integrity.json`. Full runs are a `## Full runs` section of `execution.md`. `run close-summary --closed` deletes the cache (`dropLogCache`) unless `logs.level: full`; a story id that is not a story id (`..`, a path) makes it throw rather than delete anything. A version 1 spec keeps every per-attempt file exactly as before; `test/integration/log-v2.test.ts` runs one history on both versions and compares every reader.
- `review-findings.ts`: Reviewer output must carry a validated `Findings (JSON)` envelope (`version: 1`). Only structured findings with `status: open`, `lens: security`, and `severity: high | critical` block PASS; free text is never interpreted as a security guard. Historical untagged notes remain readable through `securityMentions`.
- `close-summary.ts` (D5): a version 2 `close-summary.md` is the record (frontmatter, now with `applied`) plus `## Outcome`, `## For the PO`, `## For developers`, `## Kaizen`, `## Delivery`. `renderCloseDocument` rewrites only Outcome (from `release-status`) and Delivery (from the record) and keeps the three prose sections the agent wrote (`sectionOf`); a section or field with nothing to say is left out, never written empty or as `—`. `run close-summary --closed` upserts the spec's one `docs/CHANGELOG.md` line (`changelogLine`, `upsertChangelog`) and writes no `docs/releases/<ID>/` or `docs/kaizen/<ID>.md`; approved lessons go to `docs/kaizen/lessons.md`. `publishPlan` posts `## For the PO` for version 2 and `release-notes.md` for version 1. Version 1 keeps `renderCloseSummary` unchanged.
- `version-notes.ts` (phase 10): `versionNotes` renders a version's release notes, pure: the `For the PO` text of each closed spec copied byte for byte (tokens are filled in one pass, so the text is never rescanned), grouped by type in the template's `types` key order (unknown types after, by name), specs by ID; an entry without text goes to `missing`, never rendered. Templates are `core/templates/shared/release/version-notes.<lang>.md` (YAML frontmatter with `group_heading`, `spec_heading`, `empty`, `types`; body tokens `{version}`, `{specs}`; an unknown token throws). `releaseVersion` accepts semver only (a leading `v` is dropped). The IO (`src/scripts/version-notes.ts`, `run version-notes`) reads the git range (the previous tag is the nearest version tag, `v[0-9]*` or `[0-9]*`), takes only `Refs` values that match `STORY_ID`, and reads everything at the range end `to` with `git show`, never the working tree: it keeps specs closed by a `docs/CHANGELOG.md` line or a story with `status: closed` (version 1 closes before the CHANGELOG), and reads the installed template (`.mandao/templates/<profile>/release/`, else the core copy; no template for `language.business` → `en`, `fallback: true`); `--write` never overwrites a differing `docs/releases/v<version>.md` without `--force`, and nothing commits, tags or publishes.
- `progress.yml` out-of-scope brake (phase 11): `pending_commits[]` and `approved_manifests[]` record `reviewed` (paths the Reviewer saw as a source diff) and `receipts` (generated files seen only as receipts, with their `origin`), from one classification of the tree (`reviewPack` in `src/scripts/review.ts`; rules in `src/scripts/review-scope.ts`). `commitPending` stops, before the overlap and manifest checks, on any file of a task's commit that is not declared (`declaredCovers` in `plan.ts`: literals cover themselves and what is under them, a glob is matched with `posix.matchesGlob` and never widened, unbounded paths cover nothing; task files are mapped into the repo like origins), not reviewed, and not a receipt in scope. A receipt is in scope when its precise origin source (`originSources`: core/overrides file of a `command:`, `persona:` or `template:` origin, or the diagram source path) is declared or reviewed, or when any Mandao content source (`core/`, `.mandao/overrides/`, `.mandao/config.yml`) is declared or reviewed in the same task; a version-only upgrade leaves its regenerated files out. `.mandao/mandao.lock` (found from the workspace home) rides only with an in-scope generated file. The JSON lists them per task in `outOfScope`. A hand commit (reconcile) that carries out-of-scope files keeps only its entry pending (`outOfScope`, error with the way out) and never blocks the other entries. An entry without `reviewed` predates the brake and is skipped, unless its approval recorded one (hand edit): then only declared files pass. Reconcile (`reconcileEntries` in `src/scripts/reconcile.ts`): an entry is closed when its task's trailer commit holds the approved content (HEAD clean, or any of the task's commits), or when it records `queued_at` and the task was committed after it; then `run commit` reports the paths that differ in `differs` (MDO-0001 T1).
- `projects[].gates.build: none` (exact, case-sensitive) declares no build step by choice, for the build gate only: `buildCommand`, `declaresNoBuild` and `projectGate` in `src/schemas/config.ts` are the only readers of the value (`run build`, baseline, gates, delivery, brief and `run commit` use them), so no path executes the string. `run commit` skips the pre-commit build and reports `builds.<project>: declared-none`; the gates log says `declared none`, not `not configured`; `run commit` still refuses when no project has a build command or `none`.
- `mockup.ts` (phase 13, pure; IO in `src/scripts/mockups.ts`, CLI `run mock-offer` in `src/cli/run-mock.ts`): `mockOffer` suggests a mock once per spec, only when the story's `projects` include a UI project (`isUiProject` in `src/scripts/ui-surface.ts`: front-end/mobile dependencies, a Flutter `pubspec.yaml`, an Xcode/Gradle project under `ios/`/`android/`, a root `*.xcodeproj`/`*.xcworkspace`, `app/src/main/AndroidManifest.xml`, a root or `app/` Gradle file applying the Android plugin, `index.html` at the root, `public/` or `src/`, or a template file under `templates/`/`views/`; `projects[].ui` overrides), `## UX references` is empty (HTML comments and placeholders such as `None`, `N/A`, `-` or an `ASSUMPTION`/`OPEN` line stating none, or no/none/without plus a design word; a bare `not` is content) and no `mock` is in `state.yml`. `--record accepted|declined [--source design|html]` writes the `mock` section once (`--force` replaces it) and refuses a version 1 spec, which keeps no decision and gets no suggestion. `mockupReadmeSchema` is `mockups/README.md` (`link`/`artboard` only with `source: design`, `files` are file paths inside `mockups/`, never `README.md`, `.` or empty segments). `mockupProblems` refuses `approve design|spec` on a `.zip` under `mockups/` (unzip it), an accepted mock without README, a listed entry that is not a regular file reached without following symlinks (`filesUnder`), the private link or any claude.ai address (scheme optional, `notclaude.ai` excluded) in the README body, or `source: design` without an export file. `currentHashes` adds every regular file under `mockups/` (symlinks skipped); `changedSince` also reports a `mockups/` file deleted after approval (other documents keep "missing hash = no claim"). `composeBrief` adds `mockup: { readme, files, source, artboard?, missing? }` for a UI project's task (never the link), or `{ readme, problem }` when the README does not parse; the review pack adds `## Approved mock` with the README body, frontmatter left out and `redactPrivateLinks` applied. `mockups/` is a version 2 layout conditional (`CONDITIONALS[].since`).
- `intake.ts` / `intake-parse.ts` / `intake-proposal.ts` (phase 14, pure; IO in `src/scripts/intake.ts`, CLI `run intake-extract|intake-check|intake-open|intake-story` in `src/cli/run-intake.ts` and `mandao intake close|clean` in `src/cli/intake.ts`; schemas in `src/schemas/intake.ts`): Markdown splits at headings (`§ A > B`, `§ (preamble)`; a heading with an empty body adds no section; a repeated path gets ` (2)`), PDF on form feeds (`p. N`, from `pdftotext -layout -enc UTF-8`, injected as `PdfText` in tests). Only PDF pages with fewer than 20 non-whitespace characters are `ocr`. Batches are consecutive sections up to `batch_chars`; native pages (`chars: null`, at most `NATIVE_MAX_PAGES` = 10: without poppler Claude Code reads a PDF only whole) are one batch. `intakeCheck` parses the proposal by heading and, with the cached `sections.json`, verifies refs and coverage; without it `references-unverified` is a warning; a cached `source.sha256` that differs from the proposal's is `source-changed`, and `intake-extract` refuses to replace a cache cut from another file or version without `--force`. IDs carry their table's prefix (C/E/I/Q); `no requirement` and `requires OCR` rows list no ID. The cache `.mandao/cache/intake/<doc>/` is named by `INTAKE_DOC`: a doc that is not a slug throws before any write or removal. `intake clean` without a doc removes a cache only when its proposals exist and are all closed.
