## Learn

<a id="l1"></a>
1. **`mandao run commit` commits only the task's declared `files`.**
   - **What happened:** T2's commit left out 12 reviewed files, including `src/skills/git-copy.ts`, `src/cli/init-files.ts`, the flag registration and the writer helpers. The commit did not build: `init.ts` imports `init-files.ts`. It was amended locally to `e777726`. T3 avoided it by staging those files first.
   - **Root cause:** the implementer has to touch files that a task's list cannot foresee, for example writes that go through `src/writer` (ADR 0007), or splits forced by the 350-line limit. The Reviewer approves that diff, but the commit script commits the plan, not the diff. Nothing compares the two.
   - The same structural check would catch the independence metric too: Kaizen reports 0 reduced-independence tasks, but the T2 log rows say "reduced independence".
<a id="l2"></a>
2. **MDO-0008's approved Standardize item 1 was never applied, so the same miss repeated.**
   - **What happened:** T1 changed `core/commands/story.md` and `specify.md`, and this repo's generated `mandao-story` and `mandao-specify` files stayed stale through implement and verify. A sync at close updated 7 files.
   - **Root cause:** MDO-0008 approved the line for `core/commands/implement.md` and left it "for a follow-up change" that was never made. An approved Kaizen item with no owner and no task lapses.
   - The sync also showed that the implementer hand-wrote `src/skills/CLAUDE.md` without the managed block. The fix was to reduce it to the block, like `src/writer/CLAUDE.md`.
<a id="l3"></a>
3. **An approval was inferred, and the work it unlocked was redone.**
   - **What happened:** an earlier session recorded `mandao approve MDO-0009 spec` because `/mandao-implement` had been run, and started T1. That session stopped with uncommitted code built on the variant C-1 rejected. Attempt 1 of T1 failed review on exactly that, and the run had to stop until the maintainer approved explicitly.
   - **Root cause:** nothing in `implement` or `approve` says what counts as an approval. The approval note itself records the inference: "approved by running /mandao-implement right after…".

## Standardize

The maintainer approved all three in the close session, and they are applied in this close to
`core/commands/implement.md`, with `mandao sync` and the regenerated diagrams.

1. `core/commands/implement.md` §1 step 7: "Before `mandao run commit`, stage with `git add --` every
   file of the reviewed diff outside the task's `files`; the commit must build on its own."
2. `core/commands/implement.md`, task done: apply MDO-0008's approved line now: "A task that edits
   `core/` runs `mandao sync` and commits the generated files with the task."
3. `core/commands/implement.md` §0 step 3: "An approval is the person's explicit word for that item, or
   their own `mandao approve`; running the next command is not one."
