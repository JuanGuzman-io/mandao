## Learn

<a id="l1"></a>
1. **Every FAIL was on an item the task stated, and the implementer reported before proving it.**
   - **What happened:** after MDO-0010's standardization, each "Done when" listed its items, and the FAILs landed on those items anyway:
     - **T2:** the task's "What" and `files:` name the story template moving to `schema_version: 2`, but it was left at 1.
     - **T3:** "Readers: `next.ts` and `approve` … their tests pass on both versions" was not tested on version 2.
     - **T5:** design D5 says only Outcome and Delivery are rewritten, but `run close-summary` deleted the lead text.
     - **T6:** the S-5.1 fixture locked every derived file, so the branch that commits unlocked diagram sources never ran.
     - **T1:** the depth rule did not follow D1, and attempt 2 left a stray `trace.ts.orig` from a manual mutation check.
   - **Root cause:** the implementer persona says "Done means the whole Definition of Done … with evidence for each item", but nothing asks for that evidence item by item. The report names the verify command and its output, and the Reviewer is the first to walk the list.
<a id="l2"></a>
2. **A path built from spec content reached a recursive delete without a security tag.**
   - **What happened:** T4 deletes the spec's local cache at close. The cache path came from the story's `id`, which was not validated, and the delete was bounded only by `dirname(dir)`. The Reviewer raised `[security/high]`: close could delete outside the cache. The task carried only `risk_tags: [public-api]`, so no Tester wrote the red tests and no item named the bound.
   - **Root cause:** `tasks` tags risk by domain (auth, payments…). A filesystem delete at a path derived from document content is input handling, but nothing asks for the `input` tag or for a "stays inside its root" item.
<a id="l3"></a>
3. **`approve design` cannot clear a story change that `next` reports.**
   - **What happened:** after the AC-7 removal (C-5) edited story.md, `run next MDO-0011` recommended `mandao approve MDO-0011 design` with "story.md changed after its approval", and it still did at close. Running that approval cannot clear it.
   - **Root cause:** `approve design` hashes story.md only while the story is draft (`src/cli/approve.ts:68-70`). `changedSince` merges the hashes of every approval row (`src/spec/next.ts:80-84`), so the old story.md hash from the first design approval stays the reference.
   - **Also seen:** during this spec, the launcher (`.mandao/bin/mandao.mjs`) ran main's build. Its `verify-plan` reported `GAP AC-7` because main cannot read `status: removed` yet; the worktree build reported none.

## Standardize

The maintainer approved all three in the close session. They are applied, with `mandao sync` and the
regenerated diagrams.

1. `core/personas/implementer.md`, "Professional discipline": "Before reporting, list each Done-when item with the test name or command output that proves it; an item without one is not done."
2. `core/commands/tasks.md` §2: "A task that builds a filesystem path from spec or story content and deletes or writes there carries the `input` risk tag and a Done-when item that the path stays inside its root."
3. `docs/backlog.md`: a new item: "`approve design` hashes every approvable document it confirms, so `next`'s 'changed after its approval' can be cleared by the command it recommends (Kaizen MDO-0011 L3)."

The session-cut proposals above are not applied: the maintainer decides on them separately (ADR 0038).
